# System Requirements Specification

## 1. Functional Requirements (FR)

### FR-1: Browser-Based Instagram Direct Messaging
* **FR-1.1**: The system must run a dedicated Playwright-driven Chromium browser instance using a persistent local user-data directory (`data/browser_profile`).
* **FR-1.2**: The system must monitor direct message threads via DOM observation without invoking Meta Graph, Instagram Private APIs, or reverse-engineered HTTP endpoints.
* **FR-1.3**: The system must detect incoming messages, identify sender handles, extract text content, and record relative message timestamps.
* **FR-1.4**: The system must dispatch validated responses into the active chat thread by focusing the message input area, simulating human-like keystroke intervals (30ms - 90ms variance), and committing the send action.
* **FR-1.5**: The system must strictly enforce idempotency. No single incoming message shall ever trigger more than one dispatched reply.

### FR-2: Cognitive Subsystems & Character Persona
* **FR-2.1**: The character must possess a configurable fictional identity, backstory, personality traits, and communication boundaries externalized in YAML (`config/character.yaml`).
* **FR-2.2**: The character must exhibit a distinct conversational voice characterized by dry, deadpan, absurd, and sarcastic humor, while maintaining genuine conversational rapport.
* **FR-2.3**: The character must never claim to be an identifiable real human being, corporate customer support agent, or generic helpful AI assistant.
* **FR-2.4**: The system must maintain a multi-tier memory architecture:
  * Short-term conversation history window.
  * Long-term factual statements about the user.
  * Explicit and inferred user preferences.
  * Conversational callbacks and shared running jokes.
* **FR-2.5**: The system must dynamically adapt its communication style to the user over time (sentence length, slang, Hinglish/vernacular mixing, punctuation, sarcasm tolerance) using a statistical confidence tracking model.
* **FR-2.6**: The system must maintain a conversation chemistry state vector (`familiarity`, `playfulness`, `sarcasm_tolerance`, `trust`) that modulates teasing intensity and verbosity.
* **FR-2.7**: The system must query a local Retrieval-Augmented Generation (RAG) index to access character lore, world knowledge, and humor exemplars.

### FR-3: AI Engine & Provider Abstraction
* **FR-3.1**: The application core must interact with LLMs exclusively via an abstract `LLMProvider` interface.
* **FR-3.2**: The primary concrete implementation must support Gemini 3.8 Flash via the official client library, communicating over HTTPS using externalized credentials (`GEMINI_API_KEY`).
* **FR-3.3**: The system must be capable of swapping providers (e.g. to OpenRouter, Ollama) without altering any conversation orchestration or character engine logic.
* **FR-3.4**: All LLM generation requests must enforce a deterministic prompt structure and request structured JSON outputs adhering to strict Pydantic schemas.

### FR-4: Output Validation & Guardrails
* **FR-4.1**: Every candidate response generated by the LLM must pass through the `ResponseValidator` before dispatch.
* **FR-4.2**: The validator must reject responses that:
  * Are blank, empty, or whitespace-only.
  * Exceed character limits (default: 400 characters for Instagram DM cadence).
  * Exhibit direct repetition of recently dispatched responses.
  * Leak internal system instructions, prompt headers, or JSON tags.
  * Violate safety boundaries (hate speech, self-harm, harassment, sexual content, criminal activity).

### FR-5: State Persistence & Fault Recovery
* **FR-5.1**: All conversational states, processed message IDs, memory entries, style observations, and audit events must persist locally in a SQLite database.
* **FR-5.2**: The system must recover smoothly across application restarts, system reboots, and network drops without re-processing previously handled messages or corrupting state.
* **FR-5.3**: Transactional integrity must be maintained using SQLite Write-Ahead Logging (WAL) and explicit database transactions.

### FR-6: Observability & Diagnostics
* **FR-6.1**: The system must produce structured, JSON-formatted logs containing correlation IDs for every inbound message lifecycle.
* **FR-6.2**: Sensitive user data (message body, contact handles) must be optionally redactable via logging configuration (`LOG_SANITIZE_MESSAGES=true`).
* **FR-6.3**: System audit events (e.g. validation rejections, challenge detections, provider timeouts) must be recorded in an `audit_events` database table.

## 2. Absolute Platform Constraints & Anti-Circumvention Policy

> [!CAUTION]
> The following constraints are non-negotiable under all operating conditions:

1. **Zero Instagram API Usage**: Meta Graph API, Instagram Basic Display API, Messenger API for Instagram, and unofficial/reverse-engineered REST/GraphQL endpoints are strictly forbidden. All interactions must proceed via the visible Chromium DOM.
2. **Absolute Anti-Circumvention Rule**: The agent must NEVER attempt to bypass, circumvent, solve, or automate around:
   * CAPTCHAs (hCaptcha, reCAPTCHA, FunCaptcha).
   * Two-factor authentication (2FA) challenges or SMS verification prompts.
   * Account security checkpoints, password confirmations, or suspicious login blocks.
   * Instagram rate-limit modals or temporary action block notices.
3. **Emergency Halt Protocol**: If any challenge, block, or security checkpoint DOM element is detected:
   * **STOP**: Immediately abort all DOM typing and pending queues.
   * **CAPTURE**: Save current DOM HTML snapshot and high-resolution screenshot to `logs/diagnostics/`.
   * **LOG**: Emit a high-priority structured error log.
   * **NOTIFY**: Flag the system state as `HALTED_CHALLENGE_DETECTED` and alert the operator.
4. **No LLM Direct Control**: The LLM shall never be given tool calls, browser handles, or direct execution authority over the browser. The LLM produces textual intents only.

## 3. Non-Functional Requirements (NFR)

* **NFR-1 (Latency)**: End-to-end response time (from DOM message detection to simulated send completion) must average under 5.0 seconds under normal network and API conditions. Context retrieval and style aggregation must complete within 250ms.
* **NFR-2 (Resource Footprint)**: The local system must operate efficiently on standard consumer hardware (minimum 8GB RAM, modern 4-core x86_64 CPU) without requiring a dedicated GPU.
* **NFR-3 (Modularity)**: Monolithic modular design. Zero external runtime infrastructure requirements (no Redis, no PostgreSQL, no RabbitMQ, no Docker/Kubernetes required for local execution).
* **NFR-4 (Security & Privacy)**: Zero credential storage in source control. Passwords and API keys must reside exclusively in `.env`. Browser profile files must be excluded from version control via `.gitignore`.
* **NFR-5 (Testability)**: All cognitive components (Prompt builder, Style analyzer, Memory manager, Humor engine, Response validator) must achieve >85% unit test code coverage with deterministic mock fixtures.
